# Доступ, логирование и список Model Run

**Дата:** 2026-09-20
**Вид:** план
**Статус:** текущий
**Основание задачи:** поручение пользователя в текущем диалоге.

## Цель и границы

Добавить при создании Model Run явный выбор сервисного аккаунта, способа
аутентификации и log group; показывать ошибки создания в закрываемом модальном
окне; по умолчанию скрывать удалённые инференсы и сделать действия в списке
компактными icon-only кнопками.

Приложение остаётся read/create-only. Редактирование и удаление не отправляют
mutation-запросы и направляют пользователя в Cloud.ru Console. Реальные Cloud.ru
ресурсы при разработке не создаются. Автоматические тесты и исполняющие шаги BDD
не меняются без отдельного согласования.

## Подтверждённый внешний контракт

Cloud.ru Console получает варианты из двух BFF-endpoint:

- `/u-api/bff-console/v1/projects/{project_id}/service-accounts` возвращает
  объект `accounts`; приложению нужны только `id`, `name`, `description` и
  `enabled`;
- `/u-api/logaas-bff-console/v1/{project_id}/log-groups` возвращает объект
  `logGroups`; приложению нужны только `id`, `name`, `description`, `status`
  и `iamStatus`.

При создании используются следующие поля:

- API-ключ: `options.auth.type = AUTHENTICATION_TYPE_KEY_BASED`;
- ключи доступа: `options.auth.type = AUTHENTICATION_TYPE_TOKEN_BASED`;
- выбранный аккаунт: `options.auth.serviceAccountId`;
- выбранная группа: `options.logGroupId`;
- аутентификация, логирование и публикация API Gateway включены через
  `isEnabledAuth`, `isEnabledLogging` и `publishApiGateway`;
- UUID секрета Hugging Face передаётся как
  `modelSource.secretLocator = {secretId, version: 1}`;
- `servingOptions.cacheOptions` передаётся пустым объектом.

Количество GPU остаётся верхнеуровневым `gpuCount`; проверка показала, что
frontend и backend уже сохраняют выбранное значение без преобразования.

## Архитектура и поток данных

Существующий ответ `/api/cloud/options` расширяется нормализованными массивами
сервисных аккаунтов и log groups. Backend получает все четыре набора Cloud.ru
options одним пользовательским действием: runtime templates, квоты, аккаунты и
группы. В браузер не передаются лишние поля ответов BFF.

В список аккаунтов включаются только записи с `enabled: true`. В список log
groups включаются только группы с `status: STATUS_ACTIVE` и
`iamStatus: IAM_STATUS_READY`. Группа с точным именем `default` отмечается как
предпочтительная для начального выбора. Если её нет, поле остаётся без выбора.

Create-запрос приложения получает обязательные `service_account_id`,
`authentication_type` и `log_group_id`. Backend проверяет UUID и допустимое
enum-значение, затем передаёт выбранные значения BFF. Актуальную доступность
аккаунта и группы проверяет Cloud.ru при создании; дополнительное повторение
четырёх options-запросов перед POST не требуется.

## Интерфейс запуска и ошибки

На странице запуска появляется блок «Доступ и логи»:

- обязательный select сервисного аккаунта без автоматически выбранной записи;
- выбор между «API-ключ» и «Ключи доступа»;
- обязательный select log group с предварительно выбранной группой `default`,
  когда она доступна.

Создание блокируется до явного выбора аккаунта и группы. Ошибка, полученная после
отправки create-запроса, показывается в доступном закрываемом modal с заголовком,
текстом ошибки и кнопкой закрытия. Валидация до отправки остаётся рядом с формой.

Неопределённый результат создания также первоначально показывается в modal, но
после его закрытия существующие pending-состояние, предупреждение и блокировка
повторного POST сохраняются до ручной проверки списка пользователем.

## Список инференсов

Страница списка по умолчанию скрывает Model Run, статус которого без учёта
регистра равен `DELETED` или оканчивается на `_DELETED`.
Выключенный переключатель «Показывать удалённые» позволяет включить их обратно,
не выполняя новый запрос.

Копирование endpoint, редактирование и удаление отображаются icon-only кнопками.
У каждой кнопки есть `aria-label`, нативная подсказка и видимый focus-state.
Кнопки редактирования и удаления сохраняют текущий безопасный сценарий: только
показывают сообщение и ссылку на Cloud.ru Console.

## Спецификации и проверка

До изменения реализации DRAFT Gherkin дополняется сценариями для:

- явного выбора сервисного аккаунта и двух типов аутентификации;
- выбора log group и автоматического предпочтения `default`;
- закрываемого modal при ошибке создания с сохранением защиты от дубля;
- скрытия удалённых по умолчанию и их отображения переключателем;
- icon-only действий без mutation-запросов.

Исполняющие шаги, fixtures и другие тесты не создаются и не запускаются.
Разрешённая проверка реализации: `uv run ruff check src/vllm_cloudru`,
`pnpm --dir frontend build` и `python3 scripts/check-repo.py`.

## Вывод и продолжение

Рекомендуемое решение расширяет существующий options-flow вместо создания трёх
независимых загрузчиков. После подтверждения этой записи нужно подготовить
пошаговый план, обновить DRAFT Gherkin, реализовать backend и frontend, затем
выполнить только разрешённые проверки без реальных create-запросов Cloud.ru.
