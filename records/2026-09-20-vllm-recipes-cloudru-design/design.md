# vLLM Recipes → Cloud.ru ML Inference — дизайн

**Дата:** 2026-09-20  
**Статус:** разделы дизайна согласованы в диалоге; письменная версия ожидает итогового просмотра пользователя.  
**Назначение:** локальное однопользовательское веб-приложение для выбора конфигурации из vLLM Recipes и создания Model Run в Cloud.ru ML Inference.

## Цель и границы

Пользователь один раз вводит параметры сервисного аккаунта Cloud.ru, выбирает модель из каталога vLLM Recipes, задаёт тип и количество GPU, настройки масштабирования и запускает Model Run. Приложение также показывает уже существующие Model Run проекта.

В MVP входят:

- каталог всех рецептов с поиском и фильтрами;
- получение конфигураций через официальный JSON API vLLM Recipes;
- просмотр требований и итоговых аргументов vLLM;
- выбор пользователем GPU, их количества, `minScale` и `maxScale`;
- предупреждение, но не запрет, при несовместимости выбранных GPU с рекомендациями рецепта;
- создание одного Cloud.ru Model Run через Console BFF;
- список уже существующих Model Run;
- безопасные неактивные действия редактирования и удаления со ссылкой на Cloud.ru Console.

В MVP не входят:

- аккаунты и многопользовательский режим;
- база данных или серверное хранение секретов;
- изменение, удаление, приостановка и возобновление Model Run;
- чат или вызов развёрнутой модели;
- Docker Run;
- автоматический запуск multi-node, disaggregated и других многопроцессных рецептов;
- расчёт стоимости и управление биллингом.

## Выбранный стек

- frontend: React, TypeScript и Vite;
- backend: Python и FastAPI;
- обращения к внешним HTTP API: `httpx`;
- продуктовые спецификации: Gherkin-сценарии в статусе `DRAFT`;
- движок и объём тестовой автоматизации не выбираются до отдельного согласования.

Приложение запускается локально. Backend по умолчанию слушает loopback-интерфейс. Во время разработки Vite проксирует `/api` в FastAPI; собранный вариант использует тот же origin.

## Архитектура

```text
React/Vite
  ├── localStorage: Cloud.ru credentials + expiresAt
  └── /api
       ↓
FastAPI
  ├── Recipes adapter → https://recipes.vllm.ai
  ├── IAM adapter     → https://iam.api.cloud.ru
  └── Model Run adapter → https://console.cloud.ru/u-api/inference/model-run/v1
```

Backend не является хранилищем. Он получает учётные данные в теле конкретного Cloud-запроса, создаёт короткоживущий клиент, выполняет операцию и освобождает данные. У приложения нет собственной БД.

### Компоненты backend

1. **Recipes adapter** загружает `/models.json`, модельный JSON и опубликованные ссылки на hardware-specific JSON. Он не собирает HTML и не конструирует несуществующие URL стратегии.
2. **Recipe translator** принимает структурированный `argv` одного процесса и переводит его в `servingOptions.dynamicalOptions.args`. Он удаляет только параметры, которыми управляет платформа Cloud.ru, например сетевой bind и порт; остальные параметры рецепта сохраняются.
3. **Cloud.ru IAM adapter** обменивает `Key ID` и `Key Secret` на IAM-токен.
4. **Cloud.ru Model Run adapter** изолирует нестабильный Console BFF и предоставляет приложению только проверку подключения, список, доступные runtime/resource options и создание.
5. **Application service** объединяет рецепт с пользовательскими GPU и scaling-параметрами, валидирует форму, формирует предупреждения и создаёт Model Run.

Console BFF выбран осознанно: опубликованная OpenAPI-спецификация управления Model Run не содержит создания, а официальный репозиторий `cloud-ru/evo-aifactory-skills` реализует полный CRUD через этот BFF. Все обращения к нему сосредоточены в одном адаптере, чтобы изменение контракта не затронуло остальное приложение.

### Внутренний HTTP API

- `GET /api/recipes` — каталог, фильтры и краткая совместимость;
- `GET /api/recipes/{organization}/{model}` — подробности и доступные опубликованные конфигурации;
- `POST /api/cloud/validate` — проверка IAM-доступа и проекта;
- `POST /api/cloud/options` — активные vLLM runtime templates, GPU-ресурсы и квоты;
- `POST /api/cloud/inferences/query` — список Model Run проекта;
- `POST /api/cloud/inferences` — проверка, подтверждение предупреждений и создание Model Run.

Cloud-операции используют `POST`, даже когда внешний BFF читает данные, чтобы учётные данные не попадали в URL, историю или access-логи.

## Источники и преобразование рецептов

Последовательность discovery соответствует опубликованной vLLM схеме:

```text
/models.json
  → /{hf_id}.json
  → recommended_command.by_hardware[hardware]
  → /{hf_id}/hw/{hardware}.json
  → recommended rendering или ссылка из alternatives
```

В каталоге видны все рецепты. Для каждого отображается один из статусов:

- **Готов к запуску** — конфигурация содержит один `vllm serve` процесс, который можно выразить одним Model Run;
- **С предупреждением** — структура поддерживается, но выбранные GPU отличаются от опубликованной рекомендации;
- **Только просмотр** — рецепт требует нескольких процессов, узлов или неподдерживаемого платформой режима.

GPU-конфигурация рецепта служит рекомендацией, а тип и количество GPU остаются
явным выбором пользователя. По согласованному правилу интеграции Cloud.ru
`tensor-parallel-size` не передаётся в dynamic arguments: tensor parallelism
определяется платформой из `gpuCount`. Расхождение с опубликованным hardware-
профилем остаётся видимым предупреждением и требует подтверждения.

Для Cloud payload:

- `frameworkType` всегда соответствует vLLM;
- `runtimeTemplateId` выбирается из активных templates Cloud.ru;
- `resourceType`, `gpuCount`, `minScale` и `maxScale` задаёт пользователь;
- обязательная для API память GPU берётся из опубликованной Cloud.ru resource option, а не угадывается по названию GPU;
- `modelSource` содержит Hugging Face organization/model из рецепта;
- `modelSource.secret` получает настроенный UUID секрета Hugging Face, если он указан;
- `servingOptions.dynamicalOptions.args` получают поддерживаемые параметры рецепта;
- аутентификация endpoint включена, логирование запросов к модели выключено.

## Учётные данные и безопасность

Первоначальная настройка содержит:

- `PROJECT_ID`;
- `Key ID` сервисного аккаунта;
- `Key Secret` сервисного аккаунта;
- необязательный `Hugging Face Secret UUID` из Cloud.ru Secret Management.

Frontend сохраняет их в `localStorage` под версионированным ключом вместе с `expiresAt`, равным времени сохранения плюс семь суток. При загрузке приложения и перед каждым Cloud-запросом просроченная запись удаляется. Пользователь может очистить её вручную раньше.

Это явный компромисс локального MVP: по выбору пользователя `Key Secret`
хранится в `localStorage` без шифрования и доступен JavaScript-коду страницы.
UI прямо предупреждает об этом и не рекомендует общий компьютер. Для снижения
риска приложение:

- не подключает сторонние скрипты, аналитику и CDN;
- использует строгую Content Security Policy;
- не отображает `Key Secret` после сохранения;
- не помещает секреты в URL, логи, исключения, telemetry или recipe cache;
- очищает чувствительные поля из ошибок внешних API;
- не сохраняет IAM-токен и не возвращает его frontend.

Сам Hugging Face token в приложение не вводится: он остаётся в Cloud.ru Secret Management, приложение хранит только UUID секрета.

## Пользовательский интерфейс

Интерфейс desktop-first и адаптивный. Визуальная система основана на предоставленном референсе: тёплый кремовый фон, белые поверхности, чёрная типографика, крупные скругления, абрикосовые, мятные, жёлтые и голубые акценты. Управляющие пиктограммы — доступные SVG; сгенерированные растровые иллюстрации используются только декоративно.

Утверждённые иллюстрации:

### Экраны

1. **Настройка.** Поля доступа, семидневный срок хранения, кнопка проверки и ручная очистка.
2. **Мои инференсы.** Имя, модель, GPU, количество, scaling, статус и endpoint каждого Model Run.
3. **Каталог.** Поиск и фильтры по провайдеру, задаче, размеру, точности и доступности автоматического запуска.
4. **Модель.** Описание, варианты, требования, статус поддержки и читаемый предпросмотр аргументов.
5. **Мастер запуска.** Имя, GPU, количество, `minScale`, `maxScale`, предупреждения, итоговый payload без секретов и подтверждение.
6. **Статус запуска.** Идентификатор, состояние, endpoint и переход в список.

Кнопки «Редактировать» и «Удалить» никогда не вызывают соответствующие методы backend или Cloud.ru. Они открывают уведомление: действие нужно выполнить в Cloud.ru Console, и дают ссылку на консоль.

Критичные действия доступны с клавиатуры, состояния не передаются одним цветом, фокус видим, а декоративным изображениям задаётся пустой `alt`.

## Ошибки и неопределённые результаты

- Неверные ключи, отсутствие роли, неверный проект, исчерпанная квота и недоступный ресурс получают отдельные пользовательские сообщения.
- Ошибка vLLM Recipes показывает повторную загрузку. Последний успешный каталог живёт только в памяти backend до перезапуска.
- `minScale` должен быть неотрицательным и не превышать `maxScale`; имя Model Run нормализуется по правилам Cloud.ru и показывается до отправки.
- Несовместимость GPU требует отдельного подтверждения. Структурно непредставимый рецепт запустить нельзя.
- Если после единственного запроса создания Cloud.ru не подтвердил результат,
  backend возвращает неопределённый статус и не пытается автоматически найти
  ресурс по имени: Console BFF не предоставляет надёжного idempotency key.
  Интерфейс предлагает обновить список Model Run и проверить результат вручную.
- Frontend сохраняет признак начатого create-запроса в `sessionStorage` до
  подтверждённого ответа. После перезагрузки или потери ответа новая отправка
  заблокирована, пока пользователь явно не подтвердит, что проверил список.
- Все ошибки проходят secret-redaction перед логированием и возвратом клиенту.

## Исполняемые требования

Продуктовое поведение фиксируется Gherkin-сценариями. Исполняющие их pytest-bdd
шаги и любая другая тестовая реализация могут быть добавлены только после
отдельного согласования точного объёма; тесты не создают платные Cloud.ru ресурсы.

Минимальный набор сценариев:

- `CFG-001`: сохранённые настройки доступны до истечения семи суток;
- `CFG-002`: просроченные настройки удаляются до Cloud-запроса;
- `CFG-003`: пользователь может досрочно удалить сохранённые настройки;
- `CAT-001`: каталог показывает все полученные рецепты и их статус поддержки;
- `CAT-002`: структурно неподдерживаемый рецепт видим, но не запускается;
- `CAT-003`: совместимый рецепт с неточным GPU-профилем доступен с предупреждением;
- `CAT-004`: каталог фильтруется по выбранным провайдеру и размеру модели;
- `INF-001`: пользователь видит существующие Model Run проекта;
- `DEP-001`: поддерживаемый рецепт создаёт один Model Run с выбранными GPU и scaling;
- `DEP-002`: несовместимый GPU требует подтверждения и после него может быть отправлен;
- `DEP-003`: UUID Hugging Face секрета передаётся без значения токена;
- `DEP-004`: неопределённый ответ создания не вызывает автоматический повтор или
  автоматическое сопоставление по имени; пользователь получает предложение
  обновить список Model Run для ручной проверки;
- `DEP-005`: выбранные variant, strategy, frontend и features определяют
  checkpoint и аргументы preview и запуска;
- `DEP-006`: multi-node и companion-конфигурации видимы, но недоступны;
- `DEP-007`: payload содержит выбранный `gpuCount`, но не содержит
  `tensor-parallel-size` в dynamic arguments;
- `DEP-008`: неизвестный или недоступный selection key отклоняется до создания;
- `DEP-009`: изменение конфигурации сбрасывает подтверждение предупреждений;
- `SAFE-001`: редактирование и удаление показывают переход в Cloud.ru Console и не вызывают mutation API;
- `SEC-001`: ответы и логи не содержат `Key Secret`, IAM-токен и значение HF-токена.

После отдельного согласования API-сценарии могут выполняться через публичную
границу FastAPI, а небольшой набор критичных UI-сценариев — в браузере:
первоначальная настройка, подтверждение предупреждения и безопасные кнопки
редактирования/удаления. Технические преобразования рецептов допускается
проверять узкими unit-тестами с двумя зафиксированными примерами JSON: обычным
single-process и неподдерживаемым multi-process.

## Критерии готовности MVP

MVP готов, когда пользователь может локально:

1. сохранить и проверить Cloud.ru-настройки;
2. увидеть полный каталог vLLM Recipes;
3. отличить автоматически запускаемые рецепты от доступных только для просмотра;
4. выбрать модель, GPU, количество и scaling;
5. подтвердить предупреждение и создать ровно один Model Run;
6. увидеть созданный и ранее существовавшие Model Run;
7. перейти в Cloud.ru Console для редактирования или удаления;
8. сверить реализацию с согласованными DRAFT-сценариями; их автоматизация
   выполняется только после отдельного согласования и без платных операций.
